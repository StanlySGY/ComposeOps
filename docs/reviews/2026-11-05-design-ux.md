# ComposeOps 设计与交互审查（2026-11-05）

本次从 `2d1b9aa` 开始审查架构和关键源码，在独立数据库上启动真实 Fastify/Vue 应用，连接本机 Docker，并建立一次性 Compose 项目验证编辑和日志。另对桌面、手机视口及离线预览执行浏览器回归。生产项目配置、AI 凭据和用户数据没有用于测试夹具。

## 设计判断

ComposeOps 适合作为个人 Compose 运维台。Vue + Fastify + SQLite 的单体部署符合单用户场景，显式纳管、编辑授权、操作审批、审计、备份以及中断结果标记提供了较好的安全基础。共享 Tool Loop、项目操作入口、弹层 Escape 管理和页面资源生命周期，比继续增加独立执行通道更容易维护。

最需要改善的是**操作结果是否可信，以及编辑过程中能否保护用户的工作**。界面已经有统一的色彩、卡片、反馈和移动导航；本次发现的主要缺陷不在配色，而在表单往返、异步保存与预览语义。只增加功能或调整视觉密度，无法解决这些问题。

信息架构仍偏宽：任务中心、长期任务、运维计划、工作流、定时任务之间存在理解成本。现有导航分组与默认折叠值得保留，下一步宜增加按任务目标进入的引导和各模块之间的明确深链，先验证使用情况，再决定是否合并入口。

## 本次修复

| 严重度 | 可复现的问题 | 修复后的行为 |
| --- | --- | --- |
| 高 | 可视化编辑仅改一个变量，却丢弃 `command`、健康检查等未展示字段，并默认添加 `unless-stopped` | 从完整配置开始，仅替换实际修改字段；保留已有端口类型、IP/协议、卷模式、环境变量继承、依赖条件和网络属性；高级映射提供代码编辑提示 |
| 高 | 编辑器切换项目、文件或清除选择直接覆盖草稿；取消离开没有结束导航 | 选择在确认后才提交；取消显式终止导航并保留草稿；退出确认之后仍可再次导航 |
| 高 | 校验、预览、保存读取不同时间的可变内容；保存期间继续输入会被错误标为已保存 | 同一次操作固定项目、文件、节点代次、内容和基线；内容变化必须重新校验/预览；提交成功只推进已提交版本的基线 |
| 高 | 切节点后旧草稿仍可能操作当前节点 | 保留原草稿并禁止保存；重新载入前提供明确提示；旧节点迟到响应不能触发保存 |
| 中 | 带标签的镜像/环境变量被直接当作“变更”，多文件中的省略服务也可能被误报移除 | 对比所选文件的已保存版本，只列出真实字段差异；按 Compose service 标签关联容器，兼容自定义容器名及带连字符的项目名 |
| 中 | 无效 YAML 的预览返回空变化，容易被当作校验成功 | 解析失败返回错误，不能伪装成无变化 |
| 中 | 认证状态接口失败后显示登录表单，长时间无响应缺少恢复路径 | 独立连接失败界面、12 秒超时、请求中止及单请求重试；恢复后读取真实认证状态 |
| 低 | 有备份仍显示“暂无备份”；读取备份失败没有局部反馈 | 正确区分列表与空态，读取失败显示错误并保留编辑内容 |
| 低 | 项目权限刚变化时旧缓存可能使配置深链被清除 | 编辑器重新查询项目权限后再判断是否可打开 |

保存前提示已明确：**保存文件不会自动重启服务**。预览以所选文件为基线，不承诺完整推断多文件合并、环境变量展开或宿主实际部署影响；这些仍需通过部署预演确认。

关键实现：

- [ComposeView.vue](../../frontend/src/views/ComposeView.vue)：草稿、路由确认、内容快照及节点隔离。
- [ServiceEditor.vue](../../frontend/src/components/compose/ServiceEditor.vue)：可视化表单无损更新。
- [compose-validator.js](../../backend/src/services/compose-validator.js)、[projects.js](../../backend/src/routes/projects.js)：基于真实文件的差异预览；Agent 配置工具同步使用该基线。
- [auth.js](../../frontend/src/stores/auth.js)、[App.vue](../../frontend/src/App.vue)：连接失败与重试。

## 验证方法与范围

本次最终验证：前端 442 项通过；后端 495 项通过、1 项按原条件跳过；桌面/手机预览浏览器回归 35 项通过、3 项按视口条件跳过；ESLint、生产构建、预览构建和 `git diff --check` 均通过。

回归覆盖真实 Vue Router 的确认/取消、连续点击、校验/预览期间修改、保存期间继续输入、节点切换、所选文件索引、表单未知字段、复杂映射和环境变量类型。后端验证无变化不误报、覆盖文件不误删其他服务、真实字段变化、容器关联和错误 YAML。

浏览器使用本地生产构建，桌面 1440×1000 与手机 390×844 检查总览、服务、日志、Agent、任务中心、设置、配置页；另运行项目已有的桌面/手机预览回归。通过受控代理返回认证 503，验证连接错误界面及恢复后点击重试。一次性真实 Compose 项目用于验证文件切换确认、保存预览、磁盘内容与运行容器状态。

没有调用付费模型，也没有对生产业务容器执行停止、恢复数据卷等破坏性测试。远程 SSH/TCP 节点的实际操作、长时间压测和多浏览器同时切节点没有在本次端到端验证范围内。

## 后续值得投入的方向

1. **请求显式绑定 Host。** 当前活动节点仍是全局状态；本次补强编辑器的浏览器内保护，不能替代后端全链路的请求级节点上下文。跨标签页/跨客户端并发需要单独设计和交错执行测试。
2. **进一步区分不可达、空集合与旧数据。** 部分发现/刷新路径仍可能把失败退化为空结果或沿用缓存；可统一加入最近成功时间、失效状态与重试入口。
3. **按领域拆分大型文件。** `db.js`、Agent 引擎和几个页面承担较多职责。优先提取可独立验证的数据库仓库层和编辑状态管理，不引入额外服务或第二套执行引擎。
4. **缩短首次使用路径。** 用“检查一个服务 → 看日志 → 修改并预览 → 查看执行记录”的任务引导连接现有功能，避免单纯继续增加一级入口。
5. **提升配置预演精度。** 当前文件差异已变得可信，但多文件合并、profiles、变量展开与真实容器配置的完整比较，仍应集中在部署预演服务实现。

本次没有改变数据库结构、既有监听端口、加密密钥配置或数据卷。发布使用原有 Compose 清单和加密覆盖文件，保留发布前数据库快照及旧镜像供回退。
