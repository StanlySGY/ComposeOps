# 事件历史筛选窗口修复（2026-11-29）

## 实际缺陷

统一事件查询先取最近 500 条再在内存筛选，导致其他类型的大量事件可以挤掉较早的 GitOps 失败。旧告警读取复用了实际最多 200 条的通知栏接口，也有同样问题。已迁移旧告警的去重只看最近 500 条统一记录，因此对应的已处置记录离开窗口后，旧告警可能重新作为未处理事件出现。

## 修复

在数据库中先按类型、级别和状态筛选，再按发生时间及 ID 限制结果；统一和旧告警合并后应用最终数量上限。旧告警按全部统一记录中的 legacyAlertId 去重，安全处理损坏 JSON 和空 ID。旧告警状态兼容映射保留，查询不修改历史记录，也不新增迁移或表结构。

依据 SQLite SELECT 文档的 WHERE、ORDER BY、LIMIT 语义实现，参考 https://www.sqlite.org/lang_select.html 。对 legacyAlertId 的查询使用非相关子查询，避免对每条候选告警重复扫描全部统一记录。

## 验证与边界

- 修复前初版 6 条回归中 3 条失败，原始失败日志保留。
- 后端全量测试 1287 通过、1 跳过、0 失败；后端 lint 和 diff 检查通过。
- 8 条回归覆盖稀有记录、旧告警窗口、跨窗口迁移去重、顺序、坏 JSON、合并上限、状态兼容和真实 Fastify API；加密 SQLite 同样通过。
- 40,000 条合成记录（统一事件与旧告警各 20,000 条）的 25 次查询，中位 103.8ms、P95 149.6ms、最大 156.5ms；目标 GitOps 记录找到，迁移重复为 0。这不是任意规模数据库的性能承诺。
- 查询计划确认旧告警使用时间索引，去重 ID 集合构建一次。未新增索引或生产写操作。
- 事件概览统计依然限定最近 500 条；本次没有把它改成全历史聚合。
