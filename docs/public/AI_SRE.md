# AI 值守：故障恢复闭环

ComposeOps 的升级方向是面向自托管应用的 AI SRE 平台。第一阶段提供持久故障事件、证据分析、人工审批处置和独立恢复验证；入口是侧栏 **观测 → AI 值守**（`/#/oncall`），总览也会展示待处理故障。

本页描述开发分支中的第一阶段能力。代码合入、镜像发布和生产部署是独立步骤，旧版已发布镜像不会因文档更新而获得这些功能。

## 如何使用

1. 在服务页纳管需要值守的 Compose 项目。观察器每 15 秒检查纳管容器，将异常退出、内存不足退出、正在反复重启、Docker 健康检查失败归并为故障事件。正常停止的容器不会仅因停止而创建故障。
2. 打开故障，查看节点、项目、容器状态、观测时间和脱敏日志。点击 **AI 分析证据** 获取根因假设、证据引用和建议。AI 服务未配置或调用失败时，监控与人工处置仍可使用。
3. 如单次重启适合当前故障，点击 **生成重启处置**，审阅固定节点和容器，再点击 **批准并入队**。没有审批时不会执行重启。
4. 观察恢复验收。Docker 确认重启命令完成后，事件仍处于验证状态。必须取得至少三次连续健康观测、跨度至少 30 秒，才能标记恢复。
5. 点击 **任务与审计** 查看授权、执行记录和恢复报告。故障恢复与长期任务报告验收分开，报告仍可由管理员审阅。

开启设置中的守护模式后，系统会自动分析尚未诊断的故障。默认由用户手动发起诊断，单个事件两次诊断至少间隔 10 分钟，并发诊断最多两个。日志与状态会先脱敏，再发送到已配置的 AI 服务；诊断结论始终是待验证的假设。

## 处置与验证边界

首个处置流程为 `container-restart-v1`：仅对记录的故障容器重启一次。每个事件只登记一项该处置，重复点击返回已有记录；取消、拒绝、失败或执行结果不明后，都不会再为同一事件自动重启。其他修复通过现有日志、AI 助手或人工维护入口处理。

执行前重新检查纳管状态、授权有效期、人工审批、拒绝策略和项目操作锁，并核对节点连接版本、Docker Engine ID、容器完整 ID、创建时间与 Compose 项目标签。授权有效期为 30 分钟。拒绝策略优先于审批，针对 `incident.restart`、`container.restart` 或 `compose.restart` 的匹配拒绝规则均会阻止该处置；允许规则不能免除人工审批。

通信中断、响应超时或执行中租约到期会产生 **执行结果未知**。此状态禁止自动重试，即使容器已健康也不会直接关闭故障。管理员须到任务详情核对实际结果并填写说明，后续仍由只读健康观测判定恢复。

验证范围必须看清：

- 配置了 `HEALTHCHECK`：验证 Docker 报告的容器健康状态，覆盖程度取决于实际探针。
- 未配置 `HEALTHCHECK`：只证明容器进程持续运行，不能证明应用接口、依赖或用户业务可用。
- 样本间断超过 60 秒、期间进程再次启动、重启次数变化、观测失败或身份变化都会打断连续健康窗口。写操作完成后两分钟仍不健康，事件转为需要人工介入。
- 容器被替换、节点身份变化或目标无法读取时保留原事件，要求人工核对；不会把同名新容器当作原目标执行或验收。

## 运行配置

观察器随后端启动，独立于通知推送开关；`DISABLE_BACKGROUND_JOBS=1` 会关闭观察器自动启动。

执行器沿用现有开关。仓库 Compose 配置将 `COMPOSEOPS_EFFECT_WORKER_ENABLED` 映射到容器内的 `OPS_EFFECT_WORKER_ENABLED`，默认启用；直接启动 Node 后端时需显式设置 `OPS_EFFECT_WORKER_ENABLED=1` 才会派发已批准操作。关闭执行器后，审批只进入队列，页面会提示执行器未运行。恢复执行器时仍会检查授权期限与目标身份。

故障、证据、审批、执行账本与报告保存在现有数据库中，迁移版本为 v22。单个故障保留首条证据和最近 100 条记录；详情显示最近 100 条。列表显示最近 100 个事件并优先显示未恢复事件，统计覆盖全部记录。应用重启后继续观察所有未恢复事件。

## 验证与演练

单元回归覆盖重复采集、持久化、节点隔离、审批前零写入、授权撤销、拒绝策略、身份变化、项目并发、未知结果、采样窗口、脱敏和页面生命周期。

真实 Docker 演练脚本 `scripts/incident-recovery-integration.mjs` 使用独立临时数据库与唯一名称的测试容器。容器无网络、端口和数据卷，通过第一次启动故障、审批后重启、连续健康采样验证闭环，结束后删除测试容器与临时数据库。

先在根目录构建前端，确认 Docker、`alpine:3.20`、`codex-browser` 和 Chromium 可用，再运行：

```sh
npm run build
SRE_EVIDENCE_DIR=/tmp/composeops-sre-evidence \
  node scripts/incident-recovery-integration.mjs
```

可通过 `CODEX_BROWSER` 指定浏览器工具路径，通过 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` 指定 Chromium 路径（默认 `/usr/bin/google-chrome`）。证据目录包含实际恢复记录和桌面、手机截图。该脚本只验证隔离测试目标，不承担生产部署。

## 后续阶段

第一阶段完成“发现 → 取证 → 诊断 → 审批 → 处置 → 验证 → 留档”。后续再扩展可配置的应用可用性目标、更多版本化修复流程、按应用授权的有界自治、可靠升级与恢复演练，以及基于历史结果的效果评估。这些能力不属于本阶段交付。
