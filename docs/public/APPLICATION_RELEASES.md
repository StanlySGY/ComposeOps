# 多服务可靠发布

“应用可靠性 → 应用发布”在同一纳管应用中选择 2 至 20 个已配置 HTTP 健康目标的单副本服务。所有应用服务必须运行且身份明确，目标镜像需事先存在于该 Docker 节点。

评审读取完整 Compose 输入，固定所有运行镜像与待更新镜像的完整 ID、所有容器身份、节点和 Engine 身份、健康目标版本。根据 `depends_on` 及服务共享 namespace 等声明生成依赖 DAG 与执行顺序；未知外部依赖或循环依赖阻止发布。评审有效 15 分钟。

用户逐服务声明“无数据迁移”或“新旧版本数据双向兼容”，填写依据。未知或不可逆数据迁移不能进入此流程。系统不能证明用户兼容声明的真实性，需事先完成应用层验证。

批准绑定完整评审指纹，回退必须提前单独勾选。单服务变更与多服务发布共享项目互斥和持久状态，不允许同时执行，也不允许绕过 Agent 拒绝策略。执行前生成完整解析后的固定镜像配置，文件为 0600、目录 0700，包含展开的环境值，应按敏感部署材料保护。

按依赖顺序逐服务执行 `up --no-deps --no-build --pull never --force-recreate`。每项都检查预期镜像、稳定容器身份、连续三次健康 HTTP 且至少 30 秒稳定，再执行下一项。更新完成后联合复验所有选中服务。

中间失败停止后续；仅在预授权且身份/配置/策略仍匹配时，按已更新服务反序恢复固定旧镜像，每步验收，最后再联合复验。回退仅限镜像，不撤销数据库、卷或外部系统写入。断流、超时、意外镜像或容器变化都保留结果未知，不自动重试或补偿。恢复执行器时亦如此。

页面显示评审、顺序、依赖原因、兼容声明、正向和回退结果。未知结果需核对全部服务后关闭，关闭不计入成功。

运行 `node scripts/release-acceptance.mjs --run-isolated-fixtures` 可构建并启动三个唯一测试服务，验证正常有序发布、中间服务失败停止后续、反向回退和最终 HTTP/镜像状态。测试端口仅绑定 127.0.0.1，退出时只清理测试项目。
