# 业务备份加密

新建的业务恢复备份必须配置独立的外置密钥环；未配置时拒绝创建备份，不降级为明文。平台 SQLite 数据库密钥和业务备份密钥分别管理。旧 gzip 备份保持可读，并在界面明确标记为历史明文备份。

在仓库、数据库目录与 Docker 数据卷之外创建权限为 0600 的 JSON 文件，例如 `/home/your-user/.config/composeops/business-backup-keys.json`：

```json
{"active":"2026-11","keys":{"2026-11":"此处填写32字节随机数的64位十六进制字符串"}}
```

使用密码学随机数生成密钥，不要从密码派生，不要打印或提交密钥。设置 `COMPOSEOPS_BUSINESS_BACKUP_KEYS_FILE` 为该外部文件的绝对路径。生产重建必须同时传入现有数据库加密覆盖文件和业务备份覆盖文件：

```sh
docker compose -f docker-compose.yml -f docker-compose.encrypted.yml \
  -f docker-compose.business-encrypted.yml up -d --build
```

直接运行后端时设置 `BUSINESS_BACKUP_KEYS_FILE`。密钥文件必须是普通文件，拒绝符号链接、组或其他用户可访问的权限、超过 16 KiB 的文件及位于仓库或数据库目录中的文件。密钥版本由 1–64 个字母、数字、下划线或横线组成，最多保留 32 个版本。

原生数据库 dump 依次经过 gzip 和 AES-256-GCM，再写入权限为 0600 的临时密文。每次生成随机 IV，文件头、版本和备份身份参与认证；导出退出码、解密认证和解压长度均验证通过后才原子发布。归档延续现有 `.gz` 文件名以兼容既有路径，实际新格式由 `COBKP001` 魔数识别，不可直接使用 gunzip。

恢复前校验已固定的 SHA-256、大小、密钥版本和备份身份。加密归档先复制为权限受限的密文，打开后删除临时路径，再对同一文件描述符完成认证和解压验证，随后才创建隔离资源。恢复从该文件描述符读取，避免原路径被替换影响恢复内容；解密数据不会落地为临时明文；历史 gzip 也会以仅保存在本次进程内的随机密钥生成验证副本，结束后销毁该密钥。恢复需要额外约一份归档大小的磁盘余量。进程崩溃可能留下 `.verify-*` 密文目录；只有核对任务已停止后才可清理。

轮换时添加新版本并修改 `active`，保留所有尚未过保留期或被演练引用的旧版本。使用文件 bind mount 时，原子替换宿主文件后需要重建面板以重新挂载；重建仍需全部覆盖文件。丢失旧密钥将使对应备份不可恢复。请将密钥环另行离线备份，勿与归档存放在同一故障域。

此功能仅保护“业务数据库与应用恢复”的原生 dump 归档。其他数据库下载、卷备份以及历史明文文件的存储策略保持各自的管理方式。
