# GitOps 自动同步案例

## 场景

Git 仓库中的 Compose 配置发生变更，希望自动同步到运行环境。

---

## 当前实际行为

1. 开发者向配置的远端分支推送提交。
2. Git 平台调用 `POST /api/v1/gitops/webhook/:id`；请求必须携带已配置的 `gitops.webhook_token`，否则 Webhook 保持关闭或返回鉴权失败。
3. ComposeOps 获取远端分支，并将本地工作区切换到仓库配置的分支及其最新提交；手动同步和自动同步使用同一条同步逻辑。
4. 页面可查看提交历史与本地 Git 漂移。回滚会将工作区切到指定提交（detached HEAD）；之后再次同步会重新挂回配置分支。启用自动同步时，下一轮同步会按远端分支恢复版本。

当前 Webhook 直接触发 Git 工作区同步，不会自动调用 Agent 审批，也不会执行 `docker compose up`、重建或重启业务容器。需要部署 Compose 变更时，仍须通过相应项目操作和审批流程执行。

## 手动源码部署

对于源码仓库本身包含 Dockerfile / Compose build 配置、需要在目标 Docker 主机本地构建的项目，可在“服务总览 → 项目卡片 → 更多操作”中手动选择“拉取源码并重建”。该操作与 GitOps 自动同步、镜像拉取和平滑镜像发布相互独立：

1. 用户二次确认后，系统检查当前分支、upstream 和完整 Git 工作区状态（包括未跟踪文件）。存在任何未提交或未跟踪内容、detached HEAD 或未配置 upstream 时立即停止，不自动 stash、清理或覆盖文件。
2. 仅执行 `git pull --ff-only`。本地分支与远端发生分叉时停止，不执行 reset 或强制覆盖。
3. 拉取成功后先执行 `docker compose config --quiet`；配置校验通过才执行 `docker compose up -d --build`。
4. 命令输出进入操作结果抽屉并记入操作记录。命令完成不代表应用健康，仍需检查容器状态、健康检查和业务数据。

该操作只对已纳管并启用 Compose 目录能力的 Local / SSH 节点开放；TCP Docker API-only 节点不能在远端执行 Git 或构建命令。Webhook 与自动同步仍然只更新工作区，不会触发源码部署。构建可能重建/中断服务，也可能运行仓库内的构建指令；本操作不自动回滚数据库、数据卷或外部系统写入。

---

## 后续部署闭环边界

Git 仓库同步只保证本地工作树跟随指定提交，不等同于运行环境已经应用该版本。部署、审批和服务健康验证属于独立步骤，不能根据 Webhook 返回成功推断容器已更新。
