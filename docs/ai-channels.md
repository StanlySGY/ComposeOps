# AI 多渠道与 New API 接入

在「设置 → AI」配置最多 12 条渠道，从上到下按优先级使用。每条渠道独立保存名称、接口地址、密钥、模型、启用状态、工具调用能力和首段响应等待时间。现有单渠道配置自动显示为「默认渠道」，保存列表时迁移，无需重新填写密钥。

## 配置与测试

1. 添加渠道，填写 OpenAI 兼容接口的地址（通常以 `/v1` 结尾）和密钥。
2. 输入模型名称，或点击模型输入框旁的刷新按钮获取该渠道的模型列表。
3. AI 助手依赖工具调用，请保留「支持工具调用」并使用支持此能力的模型。关闭后，该渠道只参与无需工具的诊断、摘要等请求。
4. 保存后点击「测试连接」。测试会发送少量模型请求，可能产生上游费用。勾选工具调用的渠道会请求一个不会实际执行的测试工具，以验证返回格式；测试始终只访问指定渠道。
5. 用上移/下移调整优先级，按需启用「故障时自动切换备用渠道」。关闭时只使用第一条已启用且配置完整的渠道；若它不支持当前请求的工具能力，明确报错。

密钥输入留空会按渠道 ID 保留已保存的值；更换地址时必须重新填写密钥。获取模型列表同样不会把旧渠道密钥发送到不同地址。列表 API 只返回掩码，个人数据导出整键排除渠道配置和检索密钥，导入也不会覆盖渠道凭据。停用保留配置，删除在保存后生效。

## 故障切换规则

- 连接错误、超时、408/429、401/403/404、5xx，以及尚未输出内容时的无效响应，可以尝试下一条渠道。400 等请求错误、用户主动取消不自动切换。
- 每条渠道在一次模型调用中最多尝试一次。首段响应默认等待 30 秒，可配置为 1–120 秒；有内容后空闲超时 45 秒，所有渠道共享 120 秒总预算。
- 连续两次可重试故障后冷却 60 秒。鉴权失败冷却 5 分钟；429 至少冷却 60 秒，并参考 `Retry-After`，最长 10 分钟。
- 冷却期间请求直接使用备用。冷却到期后，由下一次实际请求探测恢复，同一渠道只放行一个恢复探测；也可手动测试立即恢复。没有后台定时探测或额外模型费用。健康状态保存在当前进程内，重启后重新观察。
- 已向前端发送回复或推理内容后中断，明确报错，不将另一渠道的内容接在后面。工具参数只有在响应完整且 JSON 合法时才交给 Agent。
- 重试只包围当前一轮模型请求。此前已经执行的工具结果原样传给备用模型，不重跑整段任务；审批门保持原有规则。聊天提示与执行轨迹会记录渠道选择、故障和跳过原因，用量按实际响应渠道配置的模型记录。

推荐主备使用独立上游，并选择工具协议和上下文容量合适的模型。接口兼容不代表所有模型能力相同；上下文过长等请求错误会直接报错，不盲目遍历全部渠道。

## 使用已有 New API

New API 可以直接作为任意一条渠道：填写 **ComposeOps 后端能够访问的网关地址 + `/v1`**、New API 创建的访问令牌，以及该令牌允许使用的模型名。在 New API 管理上游渠道、模型映射和优先级；ComposeOps 通过兼容接口调用它。

容器内的 `127.0.0.1` 指向 ComposeOps 容器自身。网关在其他容器时需要可达的宿主地址或共享 Docker 网络内的服务名。无需把 New API 的管理令牌或各上游密钥复制到 ComposeOps。

如果 New API 负责网关内部重试，建议在 ComposeOps 配置另一条独立网关或直连备用，以覆盖网关本身不可用的情况。注意两层重试会增加等待和请求次数；ComposeOps 的总时间预算依然生效。
